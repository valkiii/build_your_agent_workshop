Block A · The model

What you actually just talked to

ModelGemma 4, Google DeepMind — April 2026
This buildgemma4:e2b — the smaller of two on-device sizes (e2b / e4b)
"e2b" means2.3B effective parameters — not the whole story, see right
On disk~7 GB — more than 2.3B params' worth, because of how it's built
Context window128K tokens available; this project caps it at 8K — plenty for one article
Modalitytext, image, audio, video — we only ever send it text

“Effective” parameters aren’t the whole file. Gemma 4’s small models use Per-Layer Embeddings — a lookup table bolted onto every layer, cheap to store, cheap to query, not part of the “active” compute spent per token. It’s what lets a file this size run this well on a laptop CPU.

And “thinking”? Gemma 4 also has an optional extended-reasoning mode — put a <|think|> token in the prompt and it writes out a chain of thought before answering.

# with the token (NOT used anywhere in this project)
<|think|>  → reasons out loud first, then answers — slower, more tokens

# what every prompt in this repo actually sends
"Return ONLY valid JSON: ..."  → straight to the answer
Lesson

No prompt in this project ever includes <|think|>. Faster and more predictable on a CPU — the same “be unambiguous” habit from earlier, this time applied to the model itself, not just its output.

Speaker note Point back at the terminal from the last two slides — that's this model. If someone asks why it doesn't "show its work" like a reasoning model would: that's the <|think|> token being deliberately left out, not a limitation of the model itself.

Block A · What is an agent?

Is this actually an agent problem?

Perceive → extract → decide → act is worth the complexity only when "decide" needs real judgment. A quick gut check ↓

✓ Good fit for an agent

The output depends on judgment a script can't cheaply encode.

  • Read a stack of PDFs and pull out the ones that actually match a research question
  • Triage support tickets by what the person actually means, not a keyword match
  • Draft a first-pass reply that references the right internal doc
  • Turn a messy meeting transcript into real action items

✗ Not an agent problem

The rule already exists — writing it down is the whole job.

  • Track a price on a page and alert if it drops below a number — a scheduled script + if/else
  • Rename ten thousand files to a fixed pattern
  • Poll an API every five minutes and log the response
  • Check that a CSV's columns match a fixed schema

Block B · Why local?

Three reasons

Privacy

Nothing you read or write leaves your laptop. No third party sees your interests, your sources, or your drafts.

Cost

Free after setup. No per-token bill, no quota, no surprise invoice for a batch job that ran long.

Offline

Works on a plane. Works when the venue wifi doesn't. The model is a file on disk, not a service you call.

Block B · Why local?

Small local models are weaker than the giant cloud ones.

That's not a footnote — it's useful. The constraint forces habits that sloppy prompting against a huge model lets you skip:

clear prompts structured output knowing when not to use the model

Block C · Do's & don'ts

What we learned building this — the hard way.

Five lessons, all from things that actually broke while making the Content Curator.

Don't

Reach for the model first

Before Scrape the blog's homepage, hand the model every link, ask it which ones are real articles.
After Check for an RSS feed first — structured, dated, reliable, free. No model call at all.
Lesson

Check for structured data before reaching for judgment. Use the model for what actually needs judgment — not for what a parser already does.

Speaker note Keep this concrete — it lands because it's a real before/after, not a hypothetical. The homepage scrape genuinely returned nav links and category pages mixed in with articles.
Don't

Trust an agent blindly on consequential actions

A general principle, even outside today's build:

If an action costs money, deletes something, or can't be undone — a human confirms first.

Lesson

Cheap to add. Easy to skip. Important not to.

Do

Give small models explicit structure

Return ONLY valid JSON — and still parse defensively, because it sometimes wraps the JSON in a markdown fence anyway.

# what the model actually returned
```json
{"approved": true, "reason": "deep technical write-up"}
```

# the fix — strip the fence, then json.loads()
content.removeprefix("```json").removesuffix("```").strip()
Lesson

Small local models aren't unreliable — they're literal. Prompting them well means being unambiguous.

Do

Design for memory, not just one run

The agent keeps a small file of every URL it has already checked:

# state.json
{ "seen_urls": [ "…/transfer-learning-for-genomic-prediction", "…/a-connectomics-milestone" ] }

Rejected articles get marked seen too — so it doesn't re-summarize the same one it already turned down, every single run, forever.

Lesson

What counts as "done" is a real design decision, not an afterthought.

Do

Expect the real internet to be messy

Broke Scraped a blog index page instead of one article — got eight headlines glued together instead of one story.
Broke Images at relative paths — /images/photo.png — silently failed to download until resolved against the page's real URL.
Lesson

Defensive coding isn't paranoia. It's what working against real, uncontrolled websites actually requires.

Speaker note ~30–45 seconds per story, told as war stories, not bullet points. Keep them specific — "eight headlines glued together" and "/images/photo.png" are what make them land. Don't genericize.

Hands-on · Getting started

The relay, step by step

Whole room · 15 minutes
  1. 1Form groups of four.
  2. 2Each person picks one role: Scout, Summarizer, Judge, or Publisher.
  3. 3I'll hand each group one printed article.
  4. 4Run it as a literal relay — Scout reads it and passes on the gist, Summarizer writes two sentences, Judge checks the summary against a written interest statement and approves or rejects it with a reason, Publisher writes the approved one onto the shared page.
  5. 5One pass through is enough — we're not perfecting it, we're feeling the loop.
Scout → Perceive

Notices the article, gets the gist.

Summarizer → Extract

Pulls out what matters, in two sentences.

Judge → Decide

Approves or rejects it against the stated interest.

Publisher → Act

Writes the approved one onto the shared page.

Speaker note Zero setup, zero debugging risk — the point is to make perceive → extract → decide → act a lived experience before anyone touches a laptop. Works identically for coders and non-coders; keep tables mixed so it's a good shared moment before the tracks split at 9:50 (see the timetable, slide 3).
